Self-critique means asking a model to evaluate its own output against a rubric and revise before returning a final answer; self-consistency means running the same prompt N times and taking a majority vote instead of trusting one sample. Both buy reliability at 2–5x the token cost of a single pass, which is only worth paying for high-stakes output — a generated edit to something a user won't carefully review, a low-trust classifier feeding an automated action, content too voluminous to manually check. The honest caveat, and the reason this isn't a free reliability upgrade: a model critiquing its own output has the same blind spots that produced the output in the first place. If it didn't know price elasticity mattered when generating a recommendation, it won't suddenly know to check for it when critiquing the same recommendation — self-critique catches a different class of error (internal inconsistency, obviously violated constraints) than the class it's blind to (whatever the model was already wrong about).

That's a stronger guarantee than self-critique gives you, and it's available here specifically because the "reasoning" being checked is deterministic code, not a model's judgment about its own judgment.

## How it works

### Move 1 — the mental model

You already know this from asking a colleague to review their own pull request one more time before requesting review, versus actually getting a second person's eyes on it — the self-review catches typos and obvious mistakes, but a second person catches the things the author was blind to precisely because they wrote it that way. Self-critique is the first kind (same author, second look); self-consistency is closer to "ask three colleagues independently and go with the majority."

```
Self-critique vs self-consistency — two different reliability plays

  self-critique:                    self-consistency:
  generate ──► critique ──► revise  generate x N ──► vote ──► answer
  (same model, 2 passes,             (same model, N passes,
   sequential, ~2x cost)              parallel, ~Nx cost)
```

### Move 2 — not yet implemented in this codebase; the closest independent-check mechanism

There is no second LLM pass here to run — no model, no output to critique. What this codebase does have, and what's worth distinguishing precisely from self-critique, is the golden eval as a genuinely independent verification of each check's behavior:

```ts
// test/eval-fixtures.test.ts:8-16
 * "Independently specified" matters: the expectations below were written
 * by reading each `mg-00N.ts` check's stated behavior and reasoning about
 * what it *should* flag for each fixture — NOT by running the engine once
 * and snapshotting whatever came out.
```

Say the distinction plainly: this is stronger than self-critique, not a weaker cousin of it. Self-critique has the model check its own output using its own judgment — if the model's understanding of the task was wrong, its critique inherits the same wrongness. The golden eval's expectations were derived independently, from the spec, by a different process than the one that produced the check's implementation — so a bug in `mg-008`'s outlier logic can be caught by the eval precisely because the eval's expected values weren't derived from `mg-008`'s own code. That independence is exactly what self-critique structurally cannot achieve when it's the same model reviewing itself.

### Move 3 — the principle

The value of any "second pass" mechanism is proportional to how independent it is from whatever produced the first pass. A spec-derived golden eval is maximally independent. A different model reviewing the first model's output is partially independent. The same model critiquing its own output is the least independent version that still counts as a second pass — useful when nothing more independent is affordable, but never a substitute for an eval or a human review where either is available.

## Elaborate

Self-consistency (Wang et al., 2022) originally showed gains on reasoning tasks by sampling multiple chain-of-thought paths and voting — it's a cheaper approximation of "ask several independent reviewers" when you can't actually get several independent reviewers, because sampling temperature gives you *some* independence even from the same model. Self-critique is a different mechanism (single model, sequential critique-then-revise) and the diminishing-returns problem is well documented: a model's critique step tends to catch surface issues (formatting, obvious constraint violations) far more reliably than it catches the substantive errors that came from the same misunderstanding that produced the first-pass output.

## Interview defense

**Q: When is self-critique worth the 2-5x token cost?**
A: When the output is high-stakes (a user won't carefully review it, or it feeds an automated action) and no cheaper independent check is available. It's not worth it where a spec-derived eval or a different reviewer could catch the same errors for less — self-critique is the fallback, not the default.

```
the answer, sketched
┌─ independent check available? ──┐
│         YES                       │  → use it (eval, human, different model)
│         NO, but output is         │  → self-critique earns its cost
│         high-stakes                │
│         NO, and low-stakes         │  → skip the second pass entirely
└──────────────────────────────────┘
```

**Q: This codebase has no self-critique loop. What's the honest reason, and what's the closest real mechanism?**
A: There's no model output to critique — the checks are deterministic. The closest real mechanism is the golden eval, and it's worth being precise that it's *stronger* than self-critique, not a version of it, because its expected values are derived independently from the check's own logic (`test/eval-fixtures.test.ts:8-16`), which is exactly the independence self-critique structurally lacks.
